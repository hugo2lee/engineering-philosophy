# Skill Routing Matrix

Use this matrix to choose a primary owner for the current engineering decision. Activate the smallest Skill that owns the decision, add a secondary only when a real dependency appears, and do not activate the entire delivery chain by default.

| User signal or decision | Primary Skill | Allowed secondary Skill | Do not activate by default | Combine or escalate when |
| --- | --- | --- | --- | --- |
| Overall engineering philosophy, uncertain Skill choice, global rule governance, or proportional process | `engineering-philosophy` | Any focused Skill that owns a discovered decision | All specialists merely because they are available | The request contains multiple independent decisions or a rule may be promoted globally |
| Ambiguous requirement, missing acceptance criteria, non-goals, or material product choice | `requirement-engineering` | `engineering-philosophy` | Planning, TDD, review, Git, and CI as ceremony | A missing answer changes behavior, compatibility, data, cost, or scope |
| New request overlaps existing requirements, capabilities, contracts, or released baselines | `requirement-engineering` | `change-planning` | Reimplementation or architecture redesign before reconciliation | The request is duplicate, compatible extension, conflict, or replacement and needs a user decision |
| Approved requirement plus repository inventory, impact analysis, dependencies, risks, and completion conditions | `change-planning` | `incremental-implementation`, `architecture-boundaries`, or `ddd-lite` | Requirement ceremony when the contract is already clear; TDD before a plan exists | The change crosses multiple layers, has migration risk, or has irreversible steps |
| Architecture pressure, dependency direction, DI, Port, Adapter, interface ownership, package direction, infrastructure isolation | `architecture-boundaries` | `ddd-lite` for a discovered invariant; `systematic-debugging` for an observed boundary failure | DDD for a technical word such as “service”; interfaces without demonstrated pressure | Evidence shows repeated change pressure, a compatibility seam, or an actual boundary defect |
| Business invariant, Entity identity, Value Object, Aggregate, lifecycle, domain event, or Bounded Context | `ddd-lite` | `requirement-engineering` for unclear behavior; `architecture-boundaries` for technical translation | Architecture merely because a repository or service exists; full DDD for simple CRUD | A business invariant crosses an adapter or models genuinely diverge across contexts |
| Large refactor, migration, compatibility period, or vertical-slice sequencing | `incremental-implementation` | `test-driven-development`, `architecture-boundaries`, or `ddd-lite` | Full rewrite, complete platform scaffolding, or a second planning document by default | Old and new paths must coexist or a safe removal condition is not yet proven |
| New focused observable behavior, Red-Green-Refactor, behavior test, or regression test implementation | `test-driven-development` | `incremental-implementation` for cross-layer slices; `systematic-debugging` when the red state is unexpected | Review or a full workflow for one trivial behavior | The behavior is clear enough to test and the change needs a service or release baseline |
| Released behavior baseline across service, persistence, outbound, or inbound boundaries | `test-driven-development` | `architecture-boundaries` for the seam; `systematic-debugging` for a failure | Duplicating every business test at every layer | A baseline fails without authorization, or authorized behavior change needs synchronized updates |
| Bug, exception, timeout, regression, unexplained behavior, failed test/build/deployment | `systematic-debugging` | `test-driven-development` for a regression test; the relevant technical Skill after evidence identifies it | Architecture redesign or broad refactoring before evidence | The failure is reproducible enough for a minimal experiment and a focused fix |
| PR/MR, diff, merge readiness, correctness, maintainability, scope, or review evidence | `code-review-and-quality` | `architecture-boundaries`, `ddd-lite`, `test-driven-development`, or `systematic-debugging` for a real finding | Debugging for a review request with no active failure | The review exposes requirement mismatch, silent plan drift, a missing baseline, or an actual defect |
| Branch, commit, tag, version, changelog, history hygiene, release traceability | `git-workflow-and-versioning` | `ci-cd-and-automation` for release automation; `code-review-and-quality` for review evidence | CI merely because a tag is mentioned | A release artifact must be verified or an immutable version is being prepared |
| Pipeline, quality gate, build/test automation, artifact identity, release verification, deployment health, rollback | `ci-cd-and-automation` | `systematic-debugging` for a failed job; `git-workflow-and-versioning` for version/tag mechanics | Git history rules or review unless requested | A gate failure is reproducible, artifact identity is uncertain, or deployment needs a stop decision |
| Repository evidence should update Agent knowledge, an artifact must be classified, or a project Skill candidate must be evaluated | `knowledge-compilation` | `architecture-boundaries`, `ddd-lite`, `code-review-and-quality`, or `ci-cd-and-automation` when those decisions are discovered | Ordinary feature implementation, debugging, review, or release work merely because the repository has documentation | The source is missing, knowledge conflicts, redaction fails, or a new task boundary is not distinguishable |
| A project rule may become a cross-project or global engineering principle | `engineering-philosophy` | `knowledge-compilation` for provenance, candidate metadata, and eval evidence | Automatic promotion from one project or one incident | Independent project evidence and a separate promotion review exist |
| Explicit Codex request to send selected local repository context to ChatGPT Web for architecture reasoning, implementation planning, or follow-up review | `chatgpt-plan-execute` | The focused engineering Skill that owns each discovered decision | Any source-code upload for an ordinary coding/planning/review request; generic browser fallbacks | The manifest is safe and the user explicitly invoked the handoff; after import, route actual engineering decisions to their normal owners |
| One trivial isolated wording or formatting change with no behavior impact | No specialist by default | `engineering-philosophy` only if proportionality is unclear | DDD, architecture, full planning, TDD, review, Git, and CI ceremony | The apparently trivial change affects a public contract or released behavior |

## Routing rules

- A keyword is a signal, not a decision. “Service”, “repository”, “interface”, “CRUD”, and “event” alone do not activate DDD or architecture work.
- A requirement conflict or overlap takes precedence over implementation planning. Reconcile behavior before selecting a design.
- An actual failure takes precedence over speculative redesign. Investigate it with `systematic-debugging` before changing architecture or process.
- A clear goal with complexity belongs to `change-planning`; a large or risky implementation then adds `incremental-implementation`.
- Architecture must be justified by demonstrated change pressure or a concrete boundary risk. A future possibility is not evidence.
- TDD starts when behavior is sufficiently clear to test. It protects implementation feedback; release baselines protect shipped contracts.
- Review compares the requirement, plan, diff, baselines, and evidence. A changed plan is acceptable when the Feature Change Record records why; silent drift is not.
- Gates are proportional. A small change may satisfy them in the task or commit; a cross-boundary release needs durable evidence.
- Use the smallest set of Skills that can own the decision and its verification evidence.
- Use `knowledge-compilation` only when the knowledge surface itself is changing; do not make it a mandatory prelude to ordinary repository work.
- Prefer updating an existing knowledge owner over creating another Skill. Generation, registration, and activation are separate decisions.
- `chatgpt-plan-execute` is explicit-only because it crosses an external data boundary. It orchestrates the planner/executor handoff but does not take ownership away from focused engineering Skills.
